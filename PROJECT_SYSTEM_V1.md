# PROJECT_SYSTEM_V1 — система проектов YarnAI V1

Версия документа: **1.0**  
Статус: **DESIGN SPECIFICATION**  
Дата: **2026-07-30**  
Область: локальная система проектов YarnAI V1

## 0. Назначение и границы

Документ определяет нормативную модель проекта YarnAI V1: состав данных, идентичность, локальное хранение, операции жизненного цикла, переносимость, автосохранение и восстановление.

Ключевые слова **ДОЛЖЕН**, **НЕЛЬЗЯ**, **СЛЕДУЕТ** и **МОЖЕТ** задают обязательность требования.

V1 имеет следующие границы:

- один локальный пользователь и одно устройство;
- работа без аккаунта и без обязательного подключения к сети;
- несколько независимых проектов;
- локальное долговременное хранение;
- ручной экспорт и импорт;
- один активный calculation snapshot проекта в каждый момент времени;
- Smart Start и Step Assistant как раздельные виды прогресса;
- отсутствие совместного редактирования и облачной синхронизации.

Документ не определяет UI, визуальный дизайн, HTTP API, серверную БД, авторизацию, оплату, совместную работу, AI-анализ или полный доменный lifecycle изделия.

Текущая реализация, где calculation и progress хранятся в `localStorage` по fingerprint, является legacy-моделью. Эта модель не считается целевой системой проектов, потому что fingerprint описывает содержание расчёта, а не пользовательский проект.

### 0.1. Связь с другими документами

- `PROJECT_LIFECYCLE.md` описывает более широкий доменный lifecycle обязательства Project. Его состояния не подменяются техническими статусами V1.
- `DATA_MODEL.md` описывает будущую расширенную предметную модель Project, Garment Definition, Artifact и связанных aggregate.
- `SYNC_ARCHITECTURE_V1.md` описывает целевую облачную и multi-device архитектуру. Настоящий документ фиксирует локальные контракты, которые позволят перейти к ней без смены идентичности проекта.

При расхождении в вопросах локального поведения проектов V1 настоящий документ имеет приоритет в пределах своей области.

## 1. Что такое проект

**Project** — долговременный пользовательский контейнер одной конкретной работы: от сохранённого расчёта и подготовки к вязанию до прогресса, завершения, осознанной остановки или архивирования.

Проект:

- переживает перезагрузку страницы, закрытие браузера и новые сессии;
- имеет собственную неизменяемую идентичность;
- объединяет метаданные, расчёты, выбранный активный расчёт и прогресс;
- является границей копирования, экспорта, импорта, архивирования и удаления;
- не зависит от названия, маршрута страницы или порядка в списке;
- может существовать локально без аккаунта и без сервера.

Проект **не является**:

- calculation fingerprint;
- одним результатом расчёта;
- текущей браузерной вкладкой или сессией;
- физическим изделием;
- названием проекта;
- записью общего пользовательского профиля;
- универсальным контейнером всех изделий пользователя.

Одинаковый расчёт может законно находиться в нескольких проектах. Один проект со временем может содержать несколько неизменяемых версий расчёта, но только одна из них является активной.

## 2. Какие данные входят в проект

### 2.1. Логическая структура

| Часть | Содержание | Правило V1 |
|---|---|---|
| Project identity | `project_id`, версия схемы | Неизменяемо |
| Metadata | название, заметка, статусы, timestamps, lineage | Изменяемо по правилам раздела 4 |
| Calculations | неизменяемые snapshots входа и результата расчёта | Не перезаписываются |
| Active calculation | ссылка на текущий snapshot | Не более одной |
| Smart Start progress | текущий шаг подготовки и признак завершения | Отдельно для calculation |
| Step Assistant progress | текущий ряд, петля, завершённые ряды, epoch | Отдельно для calculation |
| Project events | значимые операции lifecycle и восстановления | Append-only до compaction |
| Recovery data | последний подтверждённый snapshot и операции после него | Системные данные |
| Integrity data | revision, checksum, версия формата | Системные данные |

### 2.2. Данные calculation snapshot

Calculation snapshot ДОЛЖЕН содержать достаточно данных, чтобы открыть проект и объяснить сохранённый результат без повторного расчёта:

- `calculation_id`;
- `project_id`;
- content fingerprint;
- исходный запрос в поддерживаемом публичном формате;
- нормализованный вход;
- полный структурированный результат;
- итоговый domain status;
- версии calculation engine, canon и specification, если они доступны;
- время создания;
- ссылку `supersedes_calculation_id`, если расчёт заменил предыдущий.

Calculation snapshot после создания НЕЛЬЗЯ редактировать. Изменение входа и новый расчёт создают новый snapshot и при явном выборе делают его активным.

Fingerprint:

- проверяет идентичность содержимого расчёта;
- МОЖЕТ совпадать в разных проектах;
- НЕЛЬЗЯ использовать как `project_id`;
- НЕЛЬЗЯ использовать как единственный ключ дедупликации проекта;
- не заменяет checksum экспортного пакета.

### 2.3. Данные прогресса

Прогресс принадлежит тройке:

`project_id + calculation_id + progress_kind`.

Поддерживаемые `progress_kind` V1:

- `SMART_START`;
- `STEP_ASSISTANT`.

Smart Start progress содержит:

- индекс текущего шага;
- признак завершения последовательности;
- `updated_at`;
- revision progress.

Step Assistant progress содержит:

- `epoch`;
- текущий ряд;
- текущую петлю;
- упорядоченный набор завершённых рядов;
- `updated_at`;
- revision progress.

`epoch` увеличивается при явном reset/rewind, который отменяет прежнюю линию прогресса. Это не позволяет будущей синхронизации ошибочно объединить прогресс до и после сброса.

Progress не переносится автоматически между разными calculation snapshots. При смене активного расчёта прежний progress сохраняется с прежним `calculation_id`, а для нового расчёта создаётся новый progress.

### 2.4. Что не входит в проект V1

В проект V1 не входят:

- access token, refresh token, пароль или cookie;
- глобальные настройки и предпочтения пользователя;
- полное содержимое `localStorage`;
- telemetry и технические журналы приложения;
- Learning State пользователя;
- данные других проектов;
- произвольный HTML или исполняемый код;
- локальные абсолютные пути;
- фотографии и видео.

Media не поддерживается в Project System V1. Для будущего расширения идентификаторы и export manifest допускают добавление media references новой версией схемы, но V1 не создаёт пустую фиктивную media-модель.

## 3. Структура идентификаторов

### 3.1. Общие правила

Все entity ID создаются на клиенте до первой записи, поэтому проект можно создать offline.

Канонический формат entity ID V1 — lowercase UUIDv7 по RFC 9562 без пользовательских префиксов и фигурных скобок:

`xxxxxxxx-xxxx-7xxx-yxxx-xxxxxxxxxxxx`

UUIDv7 выбран потому, что он:

- глобально уникален без центрального сервера;
- сортируется приблизительно по времени создания;
- принимается нативным UUID-типом будущей БД;
- не раскрывает название, email или содержание проекта.

Если среда не может безопасно создать UUIDv7, создание проекта ДОЛЖНО завершиться контролируемой ошибкой. Нельзя подменять ID timestamp, счётчиком, title, fingerprint или случайной короткой строкой.

### 3.2. Типы идентификаторов

| Идентификатор | Назначение | Меняется при дублировании | Меняется при экспорте |
|---|---|---:|---:|
| `project_id` | Идентичность проекта | Да | Нет |
| `calculation_id` | Идентичность immutable calculation snapshot | Да, создаётся snapshot-копия | Нет |
| `operation_id` | Идемпотентная значимая операция | Да | Нет |
| `export_id` | Идентичность одного сформированного export package | Новый при каждом экспорте | — |
| `source_project_id` | Lineage копии или collision-import | Сохраняет исходный ID | Нет |

### 3.3. Project ID и fingerprint

`project_id` отвечает на вопрос «какой это пользовательский проект?».

`fingerprint` отвечает на вопрос «совпадает ли нормативное содержание этих calculation snapshots?».

Из совпадения fingerprint НЕЛЬЗЯ делать вывод, что:

- проекты являются дубликатами;
- progress можно объединить;
- один проект можно удалить;
- импорт уже выполнен;
- один проект должен заменить другой.

### 3.4. Timestamps и revision

- Timestamps хранятся в UTC как строгие ISO 8601 строки с миллисекундами и суффиксом `Z`.
- Клиентское время используется для отображения и локальной сортировки, но не является глобальным concurrency authority.
- `revision` — целое положительное число, монотонно увеличиваемое при каждой подтверждённой мутации aggregate.
- Переименование, изменение заметки, статуса, активного расчёта или progress увеличивает соответствующую revision.
- Простое чтение не увеличивает content revision.

## 4. Метаданные проекта

### 4.1. Обязательные поля

| Поле | Тип / допустимые значения | Семантика |
|---|---|---|
| `schema_version` | `1` | Версия Project System schema |
| `project_id` | UUIDv7 | Неизменяемая идентичность |
| `title` | Непустая строка | Пользовательское название |
| `notes` | Строка | Необязательная заметка |
| `workspace_status` | enum | Техническое состояние V1 |
| `status_before_archive` | enum или `null` | Состояние для восстановления |
| `status_before_delete` | enum или `null` | Состояние для восстановления из корзины |
| `active_calculation_id` | UUIDv7 или `null` | Активный calculation snapshot |
| `created_at` | timestamp | Время создания |
| `updated_at` | timestamp | Последняя содержательная мутация |
| `last_opened_at` | timestamp или `null` | Последнее успешное открытие |
| `archived_at` | timestamp или `null` | Время архивирования |
| `deleted_at` | timestamp или `null` | Время soft delete |
| `purge_after` | timestamp или `null` | Не раньше какого времени допустим purge |
| `revision` | integer ≥ 1 | Локальная версия aggregate |
| `duplicated_from_project_id` | UUIDv7 или `null` | Lineage копии |
| `imported_from_project_id` | UUIDv7 или `null` | Lineage collision-import |

### 4.2. Workspace status

`workspace_status` — технический статус доступности и работы в V1, а не полная предметная модель из `PROJECT_LIFECYCLE.md`.

| Статус | Значение |
|---|---|
| `DRAFT` | Проект создан, работа по активному расчёту не начата |
| `ACTIVE` | Есть начатая текущая работа |
| `PAUSED` | Работа явно приостановлена |
| `COMPLETED` | Пользователь явно отметил работу завершённой |
| `ARCHIVED` | Проект скрыт из основного рабочего набора |
| `DELETED` | Проект находится в корзине до purge |

Допустимые основные переходы:

- `DRAFT → ACTIVE`;
- `ACTIVE ↔ PAUSED`;
- `ACTIVE → COMPLETED`;
- `DRAFT|ACTIVE|PAUSED|COMPLETED → ARCHIVED`;
- `ARCHIVED → status_before_archive`;
- любое состояние, кроме `DELETED`, → `DELETED`;
- `DELETED → status_before_delete`;
- `DELETED → purge` после retention period.

### 4.3. Ограничения полей

Title:

- после Unicode normalization NFC и trim должен содержать от 1 до 120 grapheme clusters;
- не обязан быть уникальным;
- может содержать Unicode;
- не участвует в ключах хранения или именах внутренних файлов;
- не должен интерпретироваться как HTML.

Notes:

- plain text;
- до 10 000 Unicode code points;
- не исполняется и не интерпретируется как markup в V1.

Системные timestamps и lineage пользователь напрямую не редактирует.

## 5. Создание нового проекта

### 5.1. Предусловие

В V1 проект создаётся из успешного финального calculation result со статусом `READY` или `READY_WITH_WARNINGS`.

Пустой проект без calculation snapshot не входит в минимальный V1. Возможность такого draft может быть добавлена новой совместимой версией.

### 5.2. Алгоритм

Создание ДОЛЖНО быть одной атомарной локальной транзакцией:

1. Проверить структуру и финальный статус calculation result.
2. Проверить или вычислить content fingerprint.
3. Создать новый `project_id`.
4. Создать новый `calculation_id`.
5. Сформировать immutable calculation snapshot.
6. Создать metadata со status `DRAFT`, revision `1` и timestamps текущей транзакции.
7. Установить `active_calculation_id`.
8. Создать начальные snapshots Smart Start и Step Assistant.
9. Добавить event `PROJECT_CREATED`.
10. Зафиксировать project, calculation, progress, event и recovery checkpoint в одной транзакции.
11. Только после успешного commit считать проект созданным.

Если любой шаг не завершён, частичного проекта быть не должно.

### 5.3. Название по умолчанию

Если пользователь не задал title, система формирует локализованное название из доступного безопасного контекста, например типа расчёта и даты.

Название по умолчанию:

- не является идентификатором;
- может совпадать с названием другого проекта;
- после создания редактируется обычным переименованием.

### 5.4. Повторное создание из того же расчёта

Создание проекта из calculation с уже известным fingerprint создаёт новый проект с новым `project_id`. Автоматическая дедупликация запрещена.

## 6. Открытие последнего проекта

### 6.1. Определение

Последний проект — последний успешно открытый проект из рабочего набора, а не последний изменённый storage key и не calculation с максимальным fingerprint.

Рабочий набор включает `DRAFT`, `ACTIVE`, `PAUSED` и `COMPLETED`. `ARCHIVED` и `DELETED` автоматически не открываются.

### 6.2. Выбор

Система хранит локальную ссылку `last_opened_project_id` вне Project aggregate.

При команде «открыть последний проект»:

1. Если `last_opened_project_id` указывает на валидный проект рабочего набора, открыть его.
2. Иначе выбрать валидный проект рабочего набора с максимальным `last_opened_at`.
3. При равенстве выбрать максимальный `updated_at`.
4. При повторном равенстве выбрать максимальный `created_at`.
5. Финальный tie-breaker — лексикографический порядок `project_id`, чтобы выбор был детерминированным.
6. Если рабочего проекта нет, вернуть состояние `NO_AVAILABLE_PROJECT`; новый проект автоматически не создавать.

### 6.3. Успешное открытие

Открытие считается успешным только после:

- чтения полного aggregate;
- проверки schema version и инвариантов;
- выполнения recovery при необходимости;
- проверки существования active calculation и связанного progress.

Только после этого обновляются `last_opened_at` и локальная ссылка. Неудачная попытка не должна вытеснять последний исправный проект.

## 7. Переименование

Переименование:

- доступно для любого проекта, кроме `DELETED`;
- применяет правила normalization и длины из раздела 4;
- не меняет `project_id`, calculation IDs, fingerprint, progress или `created_at`;
- обновляет `updated_at` и project revision;
- создаёт event `PROJECT_RENAMED` без хранения секретных данных;
- сохраняется атомарно.

Одинаковые titles разрешены. Система НЕЛЬЗЯ:

- добавлять скрытый suffix ради уникальности при обычном rename;
- использовать новое title как storage key;
- создавать новый проект при rename;
- менять порядок проектов иначе, чем это следует из выбранной сортировки.

Пустое или невалидное title отклоняется; прежнее title остаётся сохранённым.

---

## 8. Дублирование

Дублирование создаёт независимый новый проект из согласованного snapshot исходного проекта.

### 8.1. Что копируется

- title с локализованным suffix «копия»;
- notes;
- активный calculation snapshot;
- при необходимости другие calculation snapshots, на которые есть обязательные внутренние ссылки;
- версии engine/canon/specification;
- content fingerprints.

### 8.2. Что не копируется

- `project_id`, calculation IDs и operation IDs;
- progress Smart Start и Step Assistant;
- workspace status;
- timestamps;
- archive/delete metadata;
- project revision;
- recovery history;
- `last_opened_at`;
- локальная ссылка на последний проект.

### 8.3. Результат

Копия:

- получает новый `project_id`;
- получает новые `calculation_id` при неизменных content fingerprints;
- получает status `DRAFT`;
- получает начальный progress с новой epoch;
- записывает `duplicated_from_project_id`;
- создаётся одной транзакцией;
- не изменяет исходный проект.

Если предложенное title превышает лимит, suffix сохраняется, а исходная часть сокращается по grapheme boundary.

Дублирование архивного проекта разрешено без его восстановления. Дублирование `DELETED` запрещено до восстановления из корзины.

---

## 9. Архивирование

Архивирование — обратимое исключение проекта из основного рабочего набора без потери содержимого.

При архивировании система:

1. Завершает pending autosave.
2. Запоминает исходный допустимый status в `status_before_archive`.
3. Устанавливает `workspace_status = ARCHIVED`.
4. Записывает `archived_at`, `updated_at`, новую revision и event.
5. Удаляет ссылку `last_opened_project_id`, если она указывала на этот проект.
6. Сохраняет calculations, progress, notes, lineage и recovery data.

Архивный проект:

- не открывается автоматически как последний;
- доступен для явного просмотра, экспорта, дублирования и восстановления;
- не считается удалённым;
- не purge-ится по времени.

Восстановление из архива возвращает `status_before_archive`. Если значение отсутствует или невалидно, безопасный fallback — `PAUSED`.

Повторное архивирование уже архивного проекта идемпотентно и не должно уничтожать исходный `status_before_archive`.

---

## 10. Удаление

### 10.1. Soft delete

Обычное удаление V1 является soft delete:

- status меняется на `DELETED`;
- исходный status записывается в `status_before_delete`;
- записываются `deleted_at` и `purge_after`;
- retention period составляет 30 суток;
- проект немедленно исчезает из рабочего и архивного наборов;
- создаётся tombstone-compatible event `PROJECT_DELETED`;
- данные остаются локально доступными только механизму восстановления и purge.

Если удаляется архивный проект, `status_before_delete` сохраняет `ARCHIVED` вместе с его `status_before_archive`.

### 10.2. Восстановление из корзины

До `purge_after` проект можно восстановить:

- без смены `project_id`;
- без потери calculations и progress;
- в `status_before_delete`;
- с очисткой `deleted_at` и `purge_after`;
- с новой revision и event `PROJECT_RESTORED_FROM_TRASH`.

Если исходный status невалиден, fallback — `PAUSED`.

### 10.3. Окончательный purge

После `purge_after` система МОЖЕТ окончательно удалить project aggregate, calculations, progress, events и recovery data.

Purge:

- не выполняется до retention deadline;
- не должен затрагивать другие проекты с тем же fingerprint;
- выполняется транзакционно;
- сохраняет минимальный локальный tombstone с `project_id`, `deleted_at`, `purged_at` и последней revision на ограниченный срок, необходимый будущей миграции;
- не обещает восстановление.

Команда «удалить безвозвратно сейчас», если будет реализована, требует отдельного явного подтверждения и не является обязательной для V1.

### 10.4. Ограничение восстановления

Если пользователь очистил site data, удалил browser profile или потерял устройство, YarnAI V1 не может гарантировать восстановление без заранее созданного export package. Это ограничение должно быть явно документировано, а не маскироваться как crash recovery.

## 11. Экспорт и импорт

### 11.1. Формат экспорта

V1 использует один UTF-8 JSON-файл с рекомендуемым расширением:

`.yarnai-project.json`

Export envelope содержит:

| Поле | Назначение |
|---|---|
| `format` | Фиксированное значение `yarnai-project` |
| `schema_version` | Major schema version, для V1 — `1` |
| `export_id` | UUIDv7 конкретного пакета |
| `exported_at` | Время создания пакета |
| `application_version` | Версия экспортирующего приложения |
| `payload` | Project metadata, calculations, progress, events и lineage |
| `payload_checksum` | SHA-256 canonical payload |

Checksum вычисляется по UTF-8 представлению `payload`, канонизированному по RFC 8785. Поле checksum не входит в собственный расчёт.

Экспорт:

- доступен для рабочего и архивного проекта;
- создаётся из одного согласованного snapshot;
- не меняет project revision;
- не содержит credentials, browser preferences или данные других проектов;
- сохраняет исходные entity IDs;
- не заявляется резервной копией всех данных YarnAI.

Экспорт `DELETED` проекта запрещён до восстановления.

### 11.2. Проверка импорта

До записи система ДОЛЖНА:

1. Ограничить размер файла по документированному лимиту реализации.
2. Разобрать JSON без исполнения содержимого.
3. Проверить `format`.
4. Проверить поддерживаемую schema version.
5. Проверить checksum.
6. Проверить все IDs, timestamps, enum и ссылки.
7. Проверить project invariants и progress invariants.
8. Проверить, что пакет не содержит запрещённых исполняемых или path-based данных.
9. Построить полный import plan.
10. Записать результат одной транзакцией.

При любой ошибке импорт отклоняется целиком. Частичный проект создавать нельзя.

### 11.3. Версии

- `schema_version = 1` импортируется напрямую.
- Более новая неизвестная major version отклоняется с причиной `UNSUPPORTED_SCHEMA_VERSION`; исходный файл не изменяется.
- Более старая поддерживаемая версия сначала мигрирует в памяти, затем валидируется как текущая.
- Import migration не перезаписывает source file.
- Неизвестные поля нельзя молча превращать в известные с иной семантикой.

### 11.4. Collision policy

Импорт никогда не перезаписывает существующий локальный проект автоматически.

Правила:

1. Если `export_id` уже успешно импортирован и checksum совпадает, операция идемпотентно сообщает `ALREADY_IMPORTED`.
2. Если `project_id` отсутствует локально, исходный `project_id` и entity IDs сохраняются.
3. Если `project_id` уже существует, импорт создаёт независимую копию с новыми project/calculation/operation IDs.
4. При collision-copy исходный ID записывается в `imported_from_project_id`.
5. Fingerprint не участвует в обнаружении project ID collision.
6. Локальные progress и metadata существующего проекта не объединяются с импортом.

Такое правило сохраняет данные и не требует premature conflict resolver в V1.

### 11.5. Безопасность импорта

- Title и notes импортируются как plain text.
- Абсолютные пути и URL не открываются автоматически.
- Импорт не выполняет код и не отправляет сеть.
- Ошибка checksum блокирует импорт.
- Невалидный progress не сбрасывается молча; импорт отклоняется.
- Сообщение об ошибке не должно выводить полный приватный payload в telemetry.

## 12. Автосохранение

### 12.1. Модель хранения

Каноническое хранилище Project System V1 — транзакционный локальный repository на базе IndexedDB.

`localStorage`:

- не является source of truth новой Project System;
- может хранить только малые некритичные preferences, включая `last_opened_project_id`;
- используется legacy-adapter для чтения существующих Smart Start/Step Assistant данных;
- не должен получать dual-write после успешного переноса проекта.

UI и workflow-логика обращаются к Storage Facade, а не к конкретным storage keys.

### 12.2. Когда сохранять

Изменения делятся на два класса.

**Немедленный durable commit:**

- создание проекта;
- переход шага, ряда или петли;
- reset/rewind;
- смена активного calculation;
- дублирование;
- архивирование и восстановление;
- удаление и восстановление из корзины;
- импорт;
- явная отметка completed/paused.

**Debounced commit:**

- редактирование title;
- редактирование notes.

Debounce не должен превышать 750 ms после последнего изменения. Дополнительно pending edit немедленно сохраняется при потере focus, `visibilitychange` в `hidden`, переходе к другому проекту и перед lifecycle operation.

`beforeunload` не считается надёжным механизмом сохранения.

### 12.3. Атомарность

Одна логическая мутация в одной IndexedDB transaction обновляет:

- materialized project/progress snapshot;
- project или progress revision;
- `updated_at`;
- append-only operation/event;
- recovery checkpoint metadata.

Либо фиксируются все части, либо ни одна.

### 12.4. Ошибка сохранения

При quota, I/O или transaction error система:

- не подтверждает сохранение;
- сохраняет dirty state в памяти, пока страница жива;
- повторяет запись с ограниченным backoff;
- не увеличивает подтверждённую revision;
- не удаляет последний известный исправный snapshot;
- запрещает destructive transition, если его предварительный save не состоялся;
- предоставляет возможность export последнего доступного согласованного snapshot.

Молчаливый fallback к пустому progress запрещён.

## 13. Восстановление после сбоя

### 13.1. Защищаемые сбои

Recovery V1 покрывает:

- аварийное закрытие вкладки или процесса;
- reload во время записи;
- исключение приложения после пользовательского действия;
- повреждение последнего materialized snapshot при наличии исправного checkpoint;
- прерванный import или duplicate transaction.

Recovery V1 не покрывает:

- ручную очистку site data;
- удаление browser profile;
- физическую потерю устройства;
- повреждение всех локальных копий;
- malware или компрометацию ОС.

Для этих случаев нужен экспорт или будущая cloud backup.

### 13.2. Recovery checkpoint

Для каждого проекта хранятся:

- последний подтверждённый materialized snapshot;
- предыдущий валидный checkpoint;
- append-only операции после checkpoint;
- checksum каждого checkpoint;
- последняя подтверждённая revision.

Должно сохраняться не менее двух валидных поколений. Старые поколения и подтверждённые операции МОГУТ compact-иться по квоте и retention policy, но compaction не удаляет единственную исправную копию.

### 13.3. Открытие после сбоя

При открытии проекта:

1. Прочитать текущий snapshot.
2. Проверить schema version, checksum и инварианты.
3. Если snapshot валиден, применить валидные операции с большей revision.
4. Если snapshot невалиден, проверить предыдущий checkpoint.
5. Восстановить максимально новую однозначную revision.
6. Сохранить повреждённую запись в quarantine до успешного нового checkpoint.
7. Создать event `PROJECT_RECOVERED`.
8. Сообщить факт восстановления и границу возможной потери данных.

Система НЕЛЬЗЯ:

- заменять повреждённый проект пустым;
- сбрасывать progress без уведомления;
- переписывать recovery checkpoint до проверки восстановленного результата;
- открывать частично валидный aggregate как полностью исправный.

### 13.4. Неоднозначное восстановление

Если существует несколько валидных, но расходящихся вариантов одной revision, автоматическое объединение запрещено. V1 сохраняет варианты и открывает последний подтверждённый checkpoint в read-only recovery state до явного выбора.

## 14. Совместимость с будущей облачной синхронизацией

V1 не реализует синхронизацию, но не должен создавать данные, которые требуют смены идентичности при переходе к cloud.

### 14.1. Обязательные свойства V1

- `project_id` и другие entity IDs создаются клиентом и глобально уникальны.
- Project ID отделён от owner, device, title и fingerprint.
- Calculation snapshots immutable.
- Progress привязан к project, calculation, kind и epoch.
- Revision монотонна.
- Значимые мутации имеют уникальный `operation_id`.
- Delete представлен tombstone до purge.
- Schema version присутствует в project, export и operation.
- Timestamps нормализованы в UTC.
- Export/import идемпотентны по `export_id` и checksum.
- Локальное хранилище скрыто за Storage Facade.
- Проект не содержит credentials.

### 14.2. Будущий owner

Локальный V1-проект является guest-owned. При первом переносе в аккаунт сервер назначит `owner_user_id`, не меняя `project_id`.

Если такой `project_id` уже существует на сервере у другого owner или payload не совпадает, сервер не должен присваивать чужой проект. Нужен collision-safe import с новым ID и сохранённым lineage.

### 14.3. Будущий outbox

Локальный event journal V1 должен быть конвертируем в outbox operations:

- `operation_id`;
- `project_id`;
- aggregate kind и ID;
- base revision;
- operation kind;
- payload;
- occurred_at;
- schema version.

V1 не должен обещать, что все локальные events автоматически пригодны для merge. Destructive действия, rewind и смена active calculation должны оставаться явными операциями, чтобы будущий sync мог создать conflict вместо last-write-wins.

### 14.4. Что нельзя делать в V1

- Нельзя переиспользовать один project ID для разных проектов.
- Нельзя менять ID при обычном export/import без collision.
- Нельзя определять актуальность только по client timestamp.
- Нельзя объединять проекты по fingerprint.
- Нельзя физически удалять проект сразу после user delete.
- Нельзя хранить progress только как одно абсолютное число без epoch/revision.
- Нельзя связывать данные с абсолютным browser path или device-specific key.

## 15. Инварианты проекта

Ни одна операция не может зафиксировать состояние, нарушающее инварианты.

### 15.1. Identity и ownership

**INV-01.** `project_id` валиден, неизменяем и уникален в локальном repository.  
**INV-02.** Title и fingerprint никогда не являются identity проекта.  
**INV-03.** Один aggregate не содержит данные другого project ID.  
**INV-04.** Lineage не создаёт ownership или право на изменение исходного проекта.

### 15.2. Calculation

**INV-05.** Каждый calculation принадлежит ровно одному проекту.  
**INV-06.** Calculation snapshot неизменяем после создания.  
**INV-07.** `active_calculation_id` равен `null` только для будущего пустого draft; в минимальном V1 он указывает на существующий calculation того же проекта.  
**INV-08.** Одинаковый fingerprint разрешён в разных проектах и разных snapshots.  
**INV-09.** Смена calculation создаёт новый snapshot, а не переписывает старый.

### 15.3. Progress

**INV-10.** Не более одного активного progress на комбинацию project, calculation, kind и epoch.  
**INV-11.** Progress не применяется к calculation с другим ID или fingerprint.  
**INV-12.** Smart Start step находится в поддерживаемом диапазоне.  
**INV-13.** Step Assistant row и stitch положительны/допустимы для working count.  
**INV-14.** Завершённые ряды уникальны, упорядочены и образуют непрерывную подтверждённую последовательность до текущего ряда.  
**INV-15.** Reset/rewind, отменяющий историю, создаёт новую epoch или явную compensating operation.

### 15.4. Lifecycle и storage

**INV-16.** `revision` увеличивается монотонно и не уменьшается после recovery/import.  
**INV-17.** `ARCHIVED` имеет `archived_at`; `DELETED` имеет `deleted_at` и `purge_after`.  
**INV-18.** Архивирование не удаляет project data.  
**INV-19.** Soft delete не удаляет данные до `purge_after`.  
**INV-20.** `DELETED` проект не открывается, не дублируется и не экспортируется до восстановления.  
**INV-21.** Любая логическая мутация фиксируется атомарно со своей revision и operation/event.  
**INV-22.** Неуспешная транзакция не оставляет частичный project aggregate.  
**INV-23.** Последний валидный recovery checkpoint нельзя перезаписать невалидным snapshot.

### 15.5. Portability

**INV-24.** Export package содержит ровно один project aggregate.  
**INV-25.** Export не содержит credentials и данные других проектов.  
**INV-26.** Import не перезаписывает существующий проект без отдельного будущего merge-протокола.  
**INV-27.** Невалидный checksum или неизвестная major schema version блокирует import.  
**INV-28.** Дублирование и collision-import создают новые entity IDs, сохраняя content fingerprint и lineage.

## 16. Пользовательские сценарии

### UC-01. Первый проект из расчёта

1. Пользователь получает финальный успешный расчёт.
2. YarnAI создаёт project и calculation IDs.
3. Calculation, начальный progress и metadata сохраняются атомарно.
4. Проект открывается как `DRAFT`.
5. После первого подтверждённого действия status становится `ACTIVE`.

**Результат:** reload открывает тот же проект с тем же ID и progress.

### UC-02. Два проекта с одинаковым расчётом

1. Пользователь дважды создаёт проект из одинаковых входных данных.
2. Fingerprints совпадают.
3. Project IDs различаются.
4. Progress изменяется независимо.

**Результат:** ни один проект не перезаписывает другой.

### UC-03. Возврат после закрытия браузера

1. Пользователь продвигается в Smart Start или Step Assistant.
2. Действие немедленно фиксируется.
3. Браузер закрывается.
4. После запуска команда открытия последнего проекта выбирает сохранённый project ID.

**Результат:** отображается последняя подтверждённая revision.

### UC-04. Переименование

1. Пользователь меняет title.
2. Изменение сохраняется после debounce или при потере focus.
3. Project ID и progress остаются прежними.

**Результат:** новое title видно после reload; совпадение с другим title допустимо.

### UC-05. Дублирование для нового изделия

1. Пользователь дублирует активный или архивный проект.
2. Система копирует calculation content и notes.
3. Копия получает новые IDs, status `DRAFT` и нулевой progress.
4. Исходный проект не меняется.

**Результат:** можно связать проекты по lineage, но работать с ними независимо.

### UC-06. Архивирование и восстановление

1. Пользователь архивирует `PAUSED` проект.
2. Проект исчезает из рабочего набора и не открывается как последний.
3. Пользователь явно восстанавливает его.

**Результат:** проект возвращается в `PAUSED` с прежним progress.

### UC-07. Удаление и корзина

1. Пользователь удаляет проект.
2. Проект получает `DELETED` и retention deadline.
3. До deadline пользователь восстанавливает его.

**Результат:** ID, calculations и progress сохранены; появляется новая revision.

### UC-08. Экспорт и перенос на другое устройство

1. Пользователь экспортирует проект в `.yarnai-project.json`.
2. На другом устройстве YarnAI проверяет schema, checksum и инварианты.
3. При отсутствии project ID импорт сохраняет исходную идентичность.

**Результат:** проект открывается локально без повторного расчёта.

### UC-09. Импорт поверх существующего ID

1. Пользователь импортирует package проекта, который уже есть локально.
2. Если package уже импортирован, система сообщает `ALREADY_IMPORTED`.
3. Если это иной export с тем же project ID, создаётся collision-copy.

**Результат:** локальные данные не перезаписаны; lineage импорта сохранён.

### UC-10. Сбой во время сохранения

1. Процесс завершается во время transaction.
2. После запуска repository проверяет текущий snapshot.
3. Незавершённая transaction отсутствует целиком либо выполняется recovery из checkpoint и journal.

**Результат:** частичного проекта нет; пользователь получает последнюю однозначно подтверждённую revision.

### UC-11. Повреждённый импорт

1. Пользователь выбирает изменённый или обрезанный export-файл.
2. Checksum или invariants не проходят.
3. Import отклоняется до записи.

**Результат:** существующие проекты не изменены.

### UC-12. Новый расчёт внутри проекта

1. Пользователь пересчитывает рабочее значение с изменёнными данными.
2. Система создаёт новый immutable calculation snapshot.
3. После явного выбора он становится active.
4. Новый progress начинается отдельно; прежний остаётся связан со старым calculation.

**Результат:** история не переписана, progress разных расчётов не смешан.

| R-10 | Autosave создаёт слишком много операций | Высокая | Среднее | Debounce text; compaction; snapshots | Слишком частые progress events |
| R-11 | Клиентские часы неверны | Средняя | Среднее | Revision и IDs важнее timestamps | Локальная сортировка по времени может выглядеть странно |
| R-12 | Новая schema ломает import | Средняя | Высокое | Versioned envelope, migrations, unknown-major reject | Долгосрочная поддержка старых пакетов |
| R-13 | Импорт исполняемого/вредоносного содержимого | Низкая | Высокое | Strict JSON, plain text, no auto-open URLs/paths | Ошибки renderer escaping |
| R-14 | Legacy migration создаёт дубликаты | Высокая | Среднее | Migration marker + deterministic source mapping | Пользователь мог вручную менять storage |
| R-15 | Будущий cloud sync требует смены IDs | Низкая | Высокое | Client UUIDs, revision, operations, tombstones | Не все V1 events могут быть auto-mergeable |
| R-16 | Purge удаляет общий calculation по fingerprint | Низкая | Высокое | Ownership по project/calculation ID, не fingerprint | Ошибка referential cleanup |
| R-17 | Recovery хранит приватные данные дольше удаления | Средняя | Высокое | Recovery data входит в purge scope; retention документирован | Локальные browser backups вне контроля приложения |
| R-18 | Неполный calculation snapshot невозможно объяснить позже | Средняя | Высокое | Хранить полный public input/result и версии engine | Старый renderer может не понимать новый result |

### 17.1. Legacy migration risk

Существующие данные имеют ключи:

- `yarnai.smartStart.calculation.v1`;
- `yarnai.smartStart.calculation.v1.{fingerprint}`;
- `yarnai.smartStart.progress.v1.{fingerprint}`;
- `yarnai.stepAssistant.progress.v1.{fingerprint}`.

Однократная миграция в Project System V1 должна:

1. Собрать только валидные calculations.
2. Создать по одному project на каждый уникальный legacy calculation record.
3. Перенести Smart Start и Step Assistant progress в соответствующий project/calculation.
4. Не считать fingerprint будущим project ID.
5. Сохранить deterministic migration marker для каждого source key.
6. Выполняться идемпотентно.
7. Не удалять legacy keys до проверки нового snapshot и отдельного безопасного cleanup-этапа.
8. Не выполнять постоянный dual-write.

Если два legacy records имеют один fingerprint и одно валидное содержимое, migration МОЖЕТ считать их одним технически продублированным source record. Она не должна объединять разные progress states без однозначного правила; при расхождении создаются независимые проекты.

## 18. Критерии готовности

Project System V1 считается готовой к реализации, когда приняты все решения этого документа и нет открытого вопроса, меняющего identity, persistence или destructive semantics.

Реализация Project System V1 считается готовой к выпуску только при выполнении всех критериев ниже.

### 18.1. Functional readiness

- [ ] Новый проект атомарно создаётся из `READY` и `READY_WITH_WARNINGS`.
- [ ] Два проекта с одинаковым fingerprint имеют разные project IDs и независимый progress.
- [ ] Последний рабочий проект детерминированно открывается после reload.
- [ ] Rename сохраняется и не меняет identity.
- [ ] Duplicate создаёт новые IDs, сбрасывает progress и сохраняет lineage.
- [ ] Archive сохраняет все данные и исключает проект из auto-open.
- [ ] Restore из archive возвращает прежний допустимый status.
- [ ] Delete создаёт recoverable tombstone на 30 суток.
- [ ] Restore из trash сохраняет identity и данные.
- [ ] Purge не затрагивает другие проекты с тем же fingerprint.
- [ ] Export создаёт валидный versioned package с checksum.
- [ ] Import валидного package восстанавливает полный проект.
- [ ] Повторный import одного export идемпотентен.
- [ ] ID collision при import не перезаписывает локальный проект.
- [ ] Новый calculation snapshot не переписывает старый progress.

### 18.2. Durability and recovery readiness

- [ ] Каждое progress action имеет immediate durable commit.
- [ ] Text autosave укладывается в 750 ms после последнего изменения.
- [ ] Lifecycle operation не продолжается после failed pre-save.
- [ ] Crash в каждой точке create/import/duplicate/delete не создаёт частичный aggregate.
- [ ] Не менее двух поколений recovery checkpoint проходят checksum validation.
- [ ] Повреждённый последний snapshot восстанавливается из последнего однозначного checkpoint.
- [ ] Невалидный progress никогда не сбрасывается молча.
- [ ] Quota и I/O errors видимы вызывающему слою и не выдаются за success.

### 18.3. Data contract readiness

- [ ] Все IDs соответствуют выбранному UUIDv7 contract.
- [ ] Все timestamps соответствуют строгому UTC ISO 8601 contract.
- [ ] Schema version есть в project, operation и export.
- [ ] Calculation snapshots immutable.
- [ ] Referential и progress invariants проверяются до commit.
- [ ] Repository migration поддерживает последнюю выпущенную schema.
- [ ] Unknown major export schema безопасно отклоняется.
- [ ] Export не содержит credentials, другие проекты или browser storage dump.

### 18.4. Legacy migration readiness

- [ ] Валидные текущие Smart Start calculations обнаруживаются.
- [ ] Оба вида legacy progress переносятся без смены значений.
- [ ] Migration повторяется без создания дубликатов.
- [ ] Расходящиеся legacy progress states не объединяются молча.
- [ ] После успешной миграции source keys не участвуют в dual-write.
- [ ] До cleanup существует проверяемый rollback/export path.

### 18.5. Future sync readiness

- [ ] Project ID не меняется при назначении будущего owner.
- [ ] Каждая значимая mutation имеет operation ID и base revision.
- [ ] Reset/rewind и delete представлены явными операциями.
- [ ] Tombstone сохраняется до retention deadline.
- [ ] Storage Facade не раскрывает UI конкретные IndexedDB/localStorage keys.
- [ ] Данные V1 можно преобразовать в Project/Calculation/Progress aggregates будущего sync-слоя без генерации нового project ID.

### 18.6. Quality gate

- [ ] Есть unit-тесты всех инвариантов и transition guards.
- [ ] Есть integration-тесты всех пользовательских сценариев раздела 16.
- [ ] Есть property/fuzz-тесты import validation и identifier collision handling.
- [ ] Есть crash-injection тесты атомарных операций.
- [ ] Есть тесты quota exceeded и corrupted storage.
- [ ] Есть round-trip тест: export → import → эквивалентный payload.
- [ ] Есть migration fixtures для всех выпущенных legacy storage variants.
- [ ] Privacy review подтверждает отсутствие credentials и cross-project leakage.
- [ ] Документированы ограничения локального хранения и необходимость экспорта.

### 18.7. Не являются критерием V1

Для готовности V1 не требуются:

- аккаунты;
- серверное хранение;
- multi-device sync;
- collaboration;
- фотографии и видео;
- автоматическое разрешение конфликтов;
- восстановление после очистки browser storage;
- полный domain lifecycle из `PROJECT_LIFECYCLE.md`;
- изменение существующего UI как часть настоящей спецификации.

## Итоговое решение

YarnAI V1 получает локальную, переносимую и восстанавливаемую систему проектов, в которой:

- проект имеет собственный client-generated UUID;
- fingerprint остаётся идентичностью calculation content;
- calculation snapshots неизменяемы;
- progress изолирован по project и calculation;
- destructive действия обратимы в пределах retention;
- export/import не перезаписывают данные молча;
- autosave и recovery основаны на атомарных транзакциях;
- локальные контракты заранее совместимы с будущим owner, outbox, tombstone и cloud sync.

Главный инвариант системы: **ни одинаковый расчёт, ни одинаковое название, ни повторный импорт не дают права смешать или потерять два пользовательских проекта**.
