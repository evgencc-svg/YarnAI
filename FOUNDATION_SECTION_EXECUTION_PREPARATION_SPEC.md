## 1. Purpose and boundaries

### Purpose

`FOUNDATION_SECTION_EXECUTION_PREPARATION` converts one live-valid, completed Stage 69 snapshot into a source-bound, explicitly confirmed, immutable **preparation contract** for the 5 cm rib section. It answers only what must be known before a later physical execution stage can be designed:

1. which rib pattern is intended;
2. whether it is worked flat or in the round;
3. for flat work, how already-cast-on stitches are allocated to edges;
4. which authoritative source-bound or explicitly user-confirmed tool is intended;
5. which user-provided instruction and exact support binding define the work;
6. whether the 100-stitch count is compatible with the chosen repeat;
7. how the physical 5 cm target is to be measured;
8. whether a non-authoritative row estimate is lawfully derivable;
9. what deterministic instruction preview the user is confirming.

### Inputs

- the live project aggregate and active calculation;
- exactly one completed Stage 69 progress record and its immutable snapshot;
- the live Stage 60, 61, and 63–68 records referenced by Stage 69 (there is no Stage 62 record in this chain);
- the completed Stage 65 plan and its `FOUNDATION_SECTION` step;
- the completed Stage 67 cast-on snapshot;
- the current confirmed gauge record when available;
- user decisions defined in section 4;
- repository expected project/progress revisions and a UUID-v7 client operation ID for every mutation.

### Output

The only terminal output is one immutable completed preparation snapshot of the schema in section 10, stored under project and calculation scope. A deterministic preview is projected from that canonical state; the DOM is never an input to the snapshot.

### In scope

- live provenance validation;
- collecting and reviewing a draft;
- repeat compatibility validation without changing stitch count;
- deterministic preview generation;
- explicit confirmation;
- immutable completion, reload/recovery, staleness and conflict handling;
- a future workspace projection and route.

### Out of scope

- starting knitting or recording rows;
- `active`, `paused`, `checking`, resume, checkpoint, or completion-of-5-cm states;
- proving that the user has reached 5 cm;
- changing 100 cast-on stitches or the 5 cm physical target;
- choosing 1×1, 2×2, flat, in-round, or a tool by hidden default;
- deriving a mandatory row target;
- teaching knit stitches, purl stitches, or rib technique;
- designing or routing to a later execution stage;
- changing Stage 69, `/saved-projects`, IndexedDB, CSP, routes, scripts, or production files in this specification task.

Stage 69 cannot be treated as execution because `ribbing` identifies only a family. It does not define a repeat, row/round semantics, edge allocation, tool, instruction authority, or measurement policy. Executing from Stage 69 would therefore require hidden product choices and could issue an instruction incompatible with the fixed 100 stitches.

### Live versus copied data

1. Copied `source`, `confirmedContext`, and provenance fields make a snapshot reproducible and auditable.
2. Every create/review/complete repository command must first re-read the aggregate and reconstruct a fresh source assessment.
3. Copied values are compared to live identity, fingerprint, scope, lifecycle, and fixed facts. They cannot make a stale source current. Storage revisions are never substituted for semantic identity/fingerprint checks.
4. A read-only completed view may render the copied immutable summary, but must also show a blocked/stale diagnostic if live validation fails.
5. DOM values are collected only through controller events, normalized by the domain service, and discarded after the canonical command is built. DOM text, visibility, dataset values, and preview strings are never persisted as authority.

Failure of any required source check is fail-closed. A missing/unavailable prerequisite is `blocked`; a previously valid source whose semantic identity, fingerprint, lifecycle, scope, active-calculation binding, or fixed fact changed is `stale`; structurally invalid persisted data is `corrupted` and mapped to a blocked UI. A storage-revision-only change causes re-read/revalidation and a write conflict when the expected revision is old; it does not automatically classify the semantic source as stale.

## 4. User-input decision tree

The UI asks only fields still absent from canonical draft state and only after source validation. It must render explicit empty placeholders; there are no preselected semantic values. The fixed baseline policies below are part of the contract and must be validated by exact identifier, never inferred from UI state or replaced by a “current/latest” alias.

| Policy | Required stable identifier |
|---|---|
| supported rib set | `foundation-rib-patterns/v1` |
| in-round edge allocation | `foundation-edge-none/v1` |
| flat edge allocation | `foundation-flat-edge-one-each-side/v1` |
| tool confirmation | `foundation-tool-confirmation/v1` |
| user-provided instruction | `foundation-user-instruction/v1` |
| measurement and physical completion | `foundation-height-measurement/v1` |
| row estimate | `foundation-row-estimate-null/v1` |

Unknown, absent, or mismatched identifiers fail closed. These identifiers version semantic rules, not localized copy.

### Order and conditional visibility

1. **Rib pattern** — the user explicitly chooses `rib_1x1` or `rib_2x2`; neither is preselected. `custom_rib` and every unknown discriminator are unsupported and must not be offered.
2. **Working method resolution** — inspect the current completed Stage 65 plan first. A confirmed `flat` or `in_round` value is locked and source-bound without asking again. If authoritative Stage 65 has `workingMethod = unknown`, the user must explicitly choose turning rows (`flat`) or rounds (`in_round`). There is no hidden default. If two authoritative current Stage 65 locations disagree, fail with `SOURCE_CONFLICT`.
3. **Edge derivation** — no independent edge control exists. `in_round` deterministically yields no edges; `flat` deterministically yields one included edge stitch at each side. A method change immediately recomputes and versions this value.
4. **Tool resolution** — reuse a tool without asking again only when the live authoritative source-chain assessment proves a non-empty, current, confirmed value and binds its source identity/fingerprint. Otherwise require the user to explicitly specify and confirm the tool used for the rib. There is no hidden default and no automatic needle-size recommendation.
5. **Instruction** — the only baseline source is `user_provided`. Require normalized, non-empty, bounded plain text, its exact support tuple, and explicit acknowledgement that it is supplied by the user and is not technically verified by YarnAI. `verified_builtin` remains unsupported and is not offered.
6. **Measurement-policy acknowledgement** — display the exact versioned measurement and later physical-completion rule and require an explicit acknowledgement. This preparation acknowledgement does not claim that 5 cm has already been reached.
7. **Review** — available only when live source validation, exact policy-version validation, tool resolution, instruction validation, and repeat compatibility all succeed. It shows fixed 100 stitches and 5 cm, allocation math, tool, user-provided instruction, exact measurement wording, and no row estimate.
8. **Explicit confirmation** — the sole transition from reviewing to completed preparation.

## 5. Stitch-repeat compatibility

### Canonical allocation

```
totalCastOnStitches = 100
edgeCount = workingMethod.value == "flat" ? 2 : 0
workingStitches = totalCastOnStitches - edgeCount
repeatLength = rib_1x1 ? 2 : 4
compatible = workingStitches > 0 && workingStitches % repeatLength == 0
repeatCount = compatible ? workingStitches / repeatLength : null
```

Rules:

- 1×1 always means repeat length 2; 2×2 always means repeat length 4.
- In-round has `edgeKind = "none"`, `edgeCount = 0`, `workingStitches = 100`, and policy `foundation-edge-none/v1`.
- Flat has `edgeKind = "one_each_side_included"`, exactly one edge stitch at each side, `edgeCount = 2`, `workingStitches = 98`, and policy `foundation-flat-edge-one-each-side/v1`. Edge stitches do not participate in the rib repeat.
- No service, controller, or repository may add, remove, round, or silently reinterpret stitches. There is no `additional_edges` option.
- An incompatible combination remains editable in `collecting` with `INCOMPATIBLE_REPEAT`, or blocks entry to `reviewing`; it can never be completed.
- The exact baseline matrix for the completed cast-on is:

| Method | Edge count | Working stitches | 1×1 (`% 2`) | 2×2 (`% 4`) |
|---|---:|---:|---|---|
| `in_round` | 0 | 100 | compatible (50 repeats) | compatible (25 repeats) |
| `flat` | 2 | 98 | compatible (49 repeats) | **incompatible** (`98 % 4 = 2`) |

This compatibility check is mandatory domain validation, not UI-only validation. The UI must not allow completion of flat 2×2, and no layer may automatically change the stitch count, edge policy, working method, or pattern.

This rule validates arithmetic only. It does not certify that a row/round instruction is technically correct; the baseline stores it as user-provided authority and states that YarnAI did not technically verify it.

## 6. Measurement policy

The immutable physical target remains exactly 5 cm. The baseline measurement and later physical-completion semantics are fully defined by `foundation-height-measurement/v1`.

The JSON object and TypeScript shape have exact keys. Additional keys or alternate values fail validation.

The required user-facing rule is: measure on the needles, in the natural unstretched state, without stretching the rib, from the physical start of the ribbing immediately after the cast-on to the current top edge of the knitted section. The physical foundation section reaches its target only when the user measures it and explicitly confirms: «Высота резинки уже не меньше 5 см» (“The rib height is already at least 5 cm”). Exact equality to 5.00 cm is not required, and no separate numeric tolerance or fictitious ± millimetres may be stored.

This preparation stage requires acknowledgement of that rule but does not itself assert physical completion. A later execution contract must preserve the same policy version and record the user's explicit physical-measurement acknowledgement. If it also records the user-entered observed value, that value remains user-reported data and must not be represented as a machine measurement.

## 7. Row estimate

`rowEstimate` is exactly `null` for every baseline draft and completed snapshot, under policy `foundation-row-estimate-null/v1`.

The existing `28 rows / 10 cm` must not be used because applicability to the exact rib pattern, working method, and edge policy is not proved by Stage 63. The UI must not calculate, persist, or display `14 rows`. Row count is never physical-completion authority.

Extending Stage 63 gauge applicability and introducing a non-null, versioned estimate are separate future work. This task does not change Stage 63 and does not define a rounding policy.

## 8. Instruction source

### Discriminated union

```ts
type InstructionSource = {
  kind: "user_provided";
  text: string;
  support: InstructionSupport;
  policyVersion: "foundation-user-instruction/v1";
  attestation: {
    explicit: true;
    authority: "user";
    yarnAiTechnicalVerification: false;
    confirmedAt: ISO8601;
  };
  contentFingerprint: `fnv1a32:${string}`;
};
```

The complete `InstructionSupport` tuple must exactly equal the selected pattern, repeat, method, edge kind, edge count, and edge-policy version. The text policy uses the repository's 10,000-code-point project-note bound and the normalization in section 4. After normalization, empty text or text above the bound is invalid. The value is inert data: it is never parsed as HTML, inserted via `innerHTML`, evaluated, fetched, or treated as executable content.

Baseline validation proves only structural/domain compatibility: the pattern is supported, the method and edge policy are known, working stitches divide by the repeat, text is present, and the binding matches the selected context. It does not semantically interpret the text and does not prove that it correctly teaches rib knitting. The contract and UX must state that the instruction is user-provided and not technically verified by YarnAI; no “instruction verified” claim is permitted.

No qualifying versioned built-in catalogue exists. `verified_builtin` is not a member of the baseline union and every such persisted/input discriminator fails closed with `INVALID_INSTRUCTION_SOURCE`. A future versioned catalogue is a separate feature; the schema needs no catalogue structure beyond retaining a discriminant-based instruction source.

## 9. Lifecycle

### Persisted lifecycle

`collecting -> reviewing -> completed` is the success path. `blocked` and `stale` are persisted conditions only for a structurally valid incomplete record. `completed` is terminal and its nested completed snapshot is immutable. `corrupted` is an effective repository/UI classification, not a value written into an untrusted record.

| From | To | Required semantics |
|---|---|---|
| none | `collecting` | source live-valid; create revision 1 draft with no semantic defaults |
| `collecting` | `collecting` | valid field edit; revision +1; exact operation idempotency; dependent invalid values cleared |
| `collecting` | `reviewing` | all required inputs normalized; exact baseline policy versions present; tool resolved; instruction structurally valid and support-bound; repeat compatible; measurement policy acknowledged; `rowEstimate = null`; preview reproducible |
| `reviewing` | `collecting` | explicit edit action or any semantic input change; confirmation is cleared |
| `reviewing` | `completed` | fresh source validation, expected revisions, exact review fingerprint, measurement acknowledgement, and explicit confirmation |
| `collecting`/`reviewing` | `blocked` | a recoverable external dependency becomes unavailable without a semantic source change; ordinary field errors, invalid policy versions, and incompatible repeats remain editable in `collecting` and do not become `blocked` |
| `collecting`/`reviewing`/`blocked` | `stale` | a previously valid bound semantic source changes; write only from a structurally valid current record with expected revisions |
| `blocked` | previous `collecting`/`reviewing` | explicit revalidation proves the identical source and the blocker is resolved; revision +1 |
| `stale` | none | terminal record; after its prerequisite Stage 69 chain is live-valid, explicit rebuild creates a new higher-epoch record linked to the stale predecessor; it never mutates stale facts |
| `completed` | none | immutable; duplicate identical completion is idempotent; any different payload conflicts |

`blocked` caused only by transient read availability may be an effective workspace projection without rewriting the last valid record. `stale` after completion is likewise an effective read projection: the completed record and snapshot remain byte-for-byte immutable and the UI blocks continuation. It must not mutate completed lifecycle to stale.

  source: SourceBinding;

The draft has exact keys even when values are null. `edgePolicy` is null only until `workingMethod` is resolved; afterwards it is deterministically derived and is never a separate user input. `rowEstimate` is always null. `reviewFingerprint` is non-null only in `reviewing`; any semantic edit returns to `collecting` and clears it. `blocker` is non-null only in `blocked`; `completedSnapshot` is non-null only in `completed`; completed has `draft = null`. The state `identity` is deterministic from kind/schema/project/calculation/epoch and Stage 69 identity/fingerprint, so editing a draft never changes identity. `revision` is the domain revision and increments once per successful non-replayed mutation; the progress envelope has its own storage revision and both are validated.

### Reload, conflict, and corruption

- Reload lists all records for the exact project/calculation/kind scope, validates envelope epoch against state epoch, rejects multiple nonterminal/current records, then validates the state fingerprint, operation receipts, and live sources before rendering.
- A collecting/reviewing draft restores exactly; browser-restored form values are overwritten from canonical state after `pageshow` synchronization, not accepted as truth.
- Expected project and progress revisions are required for mutation. Mismatch returns `REVISION_CONFLICT` and preserves both stored and unsaved data.
- An existing client operation ID in `state.operations` with the same command and canonical payload fingerprint returns the prior result without a revision increment. The same ID with a different command/payload returns `OPERATION_ID_CONFLICT`. The repository-generated `operations.operation_id` is separate and remains the durable mutation envelope key.
- Malformed draft/completed data is never auto-repaired, default-filled, or discarded. It is quarantined/blocked through the repository's existing import/corruption conventions.
- On a write race, the repository re-reads the record. It returns a replay only if the client operation receipt matches exactly; otherwise it returns `REVISION_CONFLICT`. Last-write-wins and “newest timestamp wins” are forbidden.

No `active`, `paused`, `checking`, row-completion, or physical-execution transition exists here.

## 11. Draft persistence

### Repository architecture

- Reuse IndexedDB version 4 and existing `progress`, `operations`, and `checkpoints` stores/indexes; no schema migration is required.
- Future progress kind: `FOUNDATION_SECTION_EXECUTION_PREPARATION` (internal contract name, not a stage number).

### Commands

Proposed repository operations are `listFoundationSectionExecutionPreparations`, `getCurrentFoundationSectionExecutionPreparation`, `ensureFoundationSectionExecutionPreparation`, `updateFoundationSectionExecutionPreparation`, and `rebuildFoundationSectionExecutionPreparation`. | completed and current | render immutable completed summary at the same route; no automatic redirect |
| completed but live-invalid | render immutable copied summary plus blocking diagnostic; no continuation/rebuild from invalid prerequisites |
| back navigation | neutral `/saved-projects` link and normal browser Back are allowed; neither mutates state |
| after completion | remain on immutable summary; the only specified destination is neutral navigation to `/saved-projects` |

## 17. Accessibility

- Group pattern, conditional method, tool, instruction, and measurement controls with semantic `fieldset`/`legend` where they form choice sets. Derived edge allocation is read-only text, not a control.
- Every input has a persistent `<label>`; help/error IDs are connected with `aria-describedby`; invalid fields receive `aria-invalid=true`.
- Conditional fields are both `hidden` and disabled when inapplicable, removed from tab order, omitted from submitted command data, and cleared canonically.
- On validation failure, focus the error summary, link each error to its control, and then allow predictable navigation to the first invalid field.
- Blocked/stale containers use an appropriate live/alert role and `tabindex=-1`, receive focus once, and do not repeatedly steal focus during input.
- All controls and review/confirmation actions work by keyboard; visible `:focus-visible` styling and adequate touch targets are required.
- Enter on a field must not bypass the separate review and explicit-confirmation steps.
- The completed heading/summary receives managed focus after successful completion; removed form controls are not focusable.
- On reload/pageshow, restore canonical state first, render conditional visibility, then restore focus to the first incomplete field or reviewing/completed heading. Native browser restoration is never persisted without domain validation.
- Dynamic preview uses `aria-live="polite"`; repetitive typing updates should be debounced or not announced until semantic validation stabilizes.

## 18. Security and CSP

- Preserve the current CSP; do not add `unsafe-inline`, `unsafe-eval`, external script/style origins, or broad `connect-src`.
- HTML loads ordered same-origin external scripts with `defer`; there are no inline scripts or event-handler attributes.
- User labels and instructions are rendered with `textContent`, `createTextNode`, and `replaceChildren`; never `innerHTML`, template injection, `document.write`, or dynamic code evaluation.
- Persist user instruction and user-provided tool label as normalized plain data under their exact baseline policies. Markup-looking text and URL-looking text still render only as inert text; do not invent blacklist semantics or corrupt legitimate knitting symbols. Any future clickable link requires a separate allowlisted provenance contract.
- A built-in catalog, if added, is a bundled/versioned local dependency. No remote fetch, community URL, AI-generated content, or external content trust is introduced without a separate source/provenance contract.
- Route and source IDs are strict allowlisted values. Error UI does not leak internal exceptions or storage details.
